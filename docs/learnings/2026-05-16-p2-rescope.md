## Step 2 — Bugs Found During Live Run

### `os.fork` not available on Windows
RQ default worker uses `os.fork()` (Unix only). Crashes immediately on Windows.
Fix: use `SimpleWorker` — `rqworker --worker-class rq.SimpleWorker`.

### `APIFY_API_TOKEN` not in environment
Running via `python -c` doesn't load `.env` automatically.
Fix: call `load_dotenv('config/.env')` explicitly before imports, or set env var in shell.

### `item.id = None` after raw SQL upsert
`upsert_items` uses raw `db.execute(sqlite_insert(...))` which bypasses ORM tracking.
SQLAlchemy never populates `id` on the in-memory objects. Downstream code using `item.id`
(e.g. ExtractorResponse FK) silently wrote NULL or matched nothing.
Fix: re-query DB by `platform_content_id` after upsert to get ORM objects with real `id` values.

### Missing `db.commit()` after extraction loop
`SessionLocal` context manager (`with session_factory() as db`) calls `session.close()` on
exit, not `session.commit()`. Flushed `ExtractorResponse` rows were discarded on every run.
Fix: explicit `db.commit()` after the extraction loop in `run_niche_scrape`.

## Step 3 — Idempotency Verification

- Upsert deduplicates correctly — no duplicate `RawContentItem` rows created across runs
- Cache works: `reparse_from_cache` returns a hit for items extracted with the current prompt fingerprint (proven via direct call on item id=1326)
- Low `items_cache_hit` in live runs is expected — Apify returns different videos from the brainrot hashtag feed each scrape; overlap is low until DB accumulates enough coverage
- Old 439 `ExtractorResponse` rows are fingerprint-stale (system prompt changed since extraction) — they will never cache-hit under the current prompt, which is correct behavior
